# 性能测量纪律：一个数字算数的六个条件

**动性能之前先读这一份**，它短。测出来的数、以及每次结论的来龙去脉在
[`bench-baselines.md`](bench-baselines.md)——那份是流水账，本份是读它和写它的规矩。

计划出处：维护者本地计划里的 P4 纪律（不随公开快照发布）。2026-09-03 从
`bench-baselines.md` [第一节 删掉这条规则](bench-baselines.md#一删掉这条规则别的信号能覆盖吗--不能)整节搬出，**正文逐字未改**：纪律是稳定规范、常读，而基线是按
时间堆积的实验记录，两者混在一份 3500 行的文档里，前者就被后者埋掉了。

⚠ **本机不是干净测量环境。** 桌面常驻负载让 GPU 在「空闲」时也有 10–23% 利用率、
encoder 引擎 12%、58–82 W。因此**绝对 ms 偏大**，而**比值类结论稳**（竞争只会制造时钟
下垂与抖动，不会凭空消除它们）。每次测量都记录 idle 基线，见 `tools/bench/gpu.py`
的 `idle_baseline()`。

## 六个条件

`tools/bench/discipline.py` 把下面每一条做成了代码里的强制项，而不是注释里的建议。
每一条都对应一次**已经发生过的**错误结论。

**长任务（分钟级以上）一般跑一次即可**；第 1、3 条的丢弃首跑与交替只针对秒级短任务。读数期间有负载异常、结果与其他读数矛盾、或差幅接近已知波动范围时，再针对性复测。

1. **丢弃首跑，按 shape 预热。** `repeat(fn, warmup=..., repeats=...)` 保留被丢弃的样本
   并打印它们——「首跑多慢」本身是数据，不该被静音。
2. **RTF 旁边必须印绝对 ms。** `Timing.render()` 不提供只印 RTF 的形式。
3. **热漂移下交替取比值，轮间交换次序，且两个次序分别聚合后取几何平均。**
   `paired_ratio` 归约的是**每轮内部的比值**。三层，缺一层就留下一种偏差：
   先跑完 A 再跑完 B 是在比较「先后」；每轮都先 A 后 B 让 B 永远白拿一次预热优势；
   **而把两个次序的比值混在一起取中位数同样消不掉那个优势**（奇数轮由多数次序决定，
   偶数轮也不是无偏估计）。次序效应是乘性的，所以只有几何平均精确抵消它。
   函数**拒绝奇数轮**，并把恢复出来的次序效应 `k` 一起报出来。推导与两次实测更正见第九节。
4. **scale check。** `scale_check()` 断言 5 倍长的输入产出约 5 倍的工作量。
   它抓的不是慢，而是**假快**：55 s 和 11 s 一样快意味着没转写完。
5. **非零退出或空产出是 FAIL 不是计时。** `refuse_empty()`。
   外部经典事故：加载失败的后端在 0.5 s 退出，铸造了一条「102× realtime」的记录。
6. **必须声明的八项配置**：`RunConfig` 的八个字段全部无默认值——
   后端 / 量化 / 设备 / 线程数 / 冷热 / 是否排除加载 / 片段长度 / **聚合方式**。

⚠ **2026-10-10 起 ASR 的 encoder 默认走 flash attention**（RTX 30 及以后、fp16；`FINESUB_CT2_FLASH_ATTENTION` 默认 `auto`）。
构造 `RefinedWhisperModel` 的探针都继承这个默认，所以那之后的 ASR 读数与更早的基线不是同一条执行路径：要和旧基线比，
就设 `FINESUB_CT2_FLASH_ATTENTION=off`；新记的读数把这次运行用的取值写进配置。管线跑出来的产物里它记在 aligned 元数据的
`fw_refine.ct2_flash_attention`。

⚠ **聚合方式必须显式声明**，因为它本身会决定结论：`min-of-N` 偏袒 CPU（没有调度噪声
底噪要跑赢），`median` 偏袒 GPU（吸收偶发的 WDDM 停顿）。`RunConfig` 拒绝在缺少
`aggregate` 的情况下构造。

## ⚠ 第七条（还没进代码）：Windows 上显存耗尽**不报错**

这一条 `discipline.py` 管不了，因为它发生在进程之外。2026-09-19 实测撞上：

同一个进程顺序跑 7 个文件，每个文件加载两遍 TorchScript 模型而从不释放（torch 的缓存
分配器不会自己把块还给驱动）。结果**不是 OOM**：

| 看到的 | 实际的 |
| --- | --- |
| `nvidia-smi` 报 **15.8 / 16.3 GiB**，六次采样全在 15807–15839 之间抖 | 这个「平台」读起来像健康的高水位，其实是**顶满了** |
| GPU 利用率 99%，没有任何异常、没有 traceback | 驱动已经把 **8 GiB 溢到共享内存**，在走 PCIe 回读 |
| 每份文件 15–25 分钟 | 本该是几分钟；**慢了一个数量级** |

⇒ 三条：

1. **`nvidia-smi` 看不见共享显存**（Windows WDDM 下它也报不出每进程显存）。
   只看它就会把「已经在颠簸」读成「还有余量」。
2. **平坦不等于健康。** 逐份采样看到的平台可能是上限而不是稳态；要判断有没有泄漏，
   得看**释放之后**的水位，不是峰值。所以长跑脚本该每轮自报 `torch.cuda.memory_reserved()`。
3. **一个不报错、只慢十倍的失败模式，会静默污染任何同期的耗时读数**——包括别人的。
   量性能之前先对一次空载基线（本仓的惯例），这条是那条惯例的理由之一。

修法不是调参，是**用完归还**：见 `speech/diarization/{runner.py 的 close(), diarizen_runtime.py 的
loaded_model(), nemotron3_backend.py 的 frame_activity()}`，每个后端各一处。
